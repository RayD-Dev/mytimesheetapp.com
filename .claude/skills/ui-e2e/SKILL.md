# UI end to end

One loop from intent to shipped front-end code: **Orient, Brief, Design, Plan, Build, Check, Close.** The main session does the thinking: briefs, plans, design calls and reviews. Sub-agents on cheaper models write the code and run the commands. The user approves four things: the brief, the mock-up, the plan, and the finished work in the browser. Checks run automatically in between.

The specialist skills do the detailed work; this one sequences them and holds the gates:

| Step | Skills |
|---|---|
| Design | ui-mockup, ui-craft, ui-motion |
| Check | ui-audit, ui-visual-check |
| Docs | docs-sync |

## Where things live

| What | Where | Master |
|---|---|---|
| PRD, HL design, system design, FE and BE design | Notion, where the user gives feedback as comments. A read-only copy is in `docs/notion/` | Notion |
| One line per requirement, decision and roadmap item | `docs/INDEX.md` | Generated by docs-sync |
| App-wide design rules, tokens, vocabulary | `DESIGN.md` | Repo |
| One spec per screen | `docs/screens/<page>.md` | Repo |
| Approved screenshots | `mockup/approved/` (index in its README) | Repo |
| Briefs and plans | `.claude/plans/work/<NNN>-<slug>/brief.md` and `plan.md` | Repo |
| Coding standards and check gates | `references/standards.md` | This skill |

Never edit `docs/notion/`. Engineering decisions go into the Notion doc's decision log, then docs-sync refreshes the copy.

## Token rules

- Start from `docs/INDEX.md`. Open a full doc only at the section the index points to.
- Read this skill's references at the step that names them, not up front.
- Read upstream skills by section only (`../ui-craft/references/upstream.md`).
- Hand work to sub-agents as `references/delegation.md` describes. Ask for short reports. Read diffs selectively: `git diff --stat` first, then only the files that matter.
- Screenshot only the routes that changed.

## 0. Orient

1. Read `docs/INDEX.md`, `DESIGN.md`, and the screen specs and work folder for the area.
2. If the user mentions changes in Notion, or `docs/INDEX.md` was synced more than a week ago and you need its facts, run docs-sync first.
3. When resuming, read `plan.md`'s task table and continue from the first unfinished task.

## 1. Brief (the user approves)

Create the work folder with the next free number and fill `brief.md` from `references/brief-template.md`.

- Every requirement cites its source: a doc and section, or "conversation, <date>" with the user's words. Intent that isn't written down anywhere gets asked about, not inferred. Ask only the questions whose answers change what gets built.
- State the goal back in one line at the top.
- Show the brief and wait for approval. Nothing is planned before then.

The brief is the intent check. The acceptance criteria become the tests in step 3, so vague criteria mean vague tests.

## 2. Design (only when screens are new or change)

- **New or changed screen:** run ui-mockup rounds until the user approves, then replace the affected screenshots in `mockup/approved/`.
- **Approved screen with no spec yet:** write `docs/screens/<page>.md` from `references/screen-spec-template.md`. Take it from the mock-up page, `mockup/ROUNDS.md` and the approved screenshots. Extraction is mechanical, so give each page to an implementer and review the result against the screenshots.
- **A deliberate change from the approved mock-up** goes in the spec's "Changes since approval" with the reason and the user's OK. Otherwise the check gate treats it as a bug.

## 3. Plan (the user approves)

1. **Settle the open engineering decisions the work depends on.** These are the TBD sections and open questions in the FE design doc, such as project structure, API client, state, testing set-up and sign-in. Propose each once with a recommendation; the user decides. Record the decision in the Notion doc's decision log, then run docs-sync.
2. **API contract.** List the endpoints and fields the work needs. The OpenAPI spec is shared with the back end. Front-end types *and* runtime response schemas are generated from it, never hand-written (`references/standards.md`). Back-end work is outside this skill: hand the contract to the back-end plan.
3. **Write `plan.md`** from `references/plan-template.md`:
   - Tasks small enough for one agent, each self-contained: files, decisions, the acceptance criteria it covers, the tests to write first, the check command, and done-when.
   - File ownership, so parallel tasks never share a file.
   - Future impact: which roadmap items touch this code, and the free seams left for them (`references/standards.md`, "Future milestones").
4. Show the plan and wait for approval.

## 4. Build

Delegate as `references/delegation.md` describes:

| Agent | Model | Does |
|---|---|---|
| implementer | Sonnet | Writes code and tests for each plan task |
| mechanic | Haiku | Fixtures, renames, wiring generated code |
| runner | Haiku | Runs checks and reports failures |
| Explore | Haiku | Finds things in the code or docs |

- **Review every diff** against the brief and plan before marking a task done. An agent's report is a claim, not proof.
- **Two failures, then take it back.** A task that fails its check twice comes back to the main session; don't retry it at the same tier.
- **Parallel only on separate files.** Tasks that don't share files run in parallel.
- **Stay inside the plan.** If building shows the plan is wrong, stop, fix the plan, and tell the user if it changes what they approved.
- **Keep security in the main session.** Sign-in, permissions, approvals and data access are reviewed line by line here.

## 5. Check (then the user tries it)

Run the gates in `references/standards.md`, "Checks". The runner does the mechanical ones; the main session judges screenshots and the critique. On every change: type-check and lint, unit tests, the ui-audit scan. At the end of a slice, all seven must pass.

Then give the user:
- the URL and a test login
- what to try
- the phone checks from ui-visual-check

Their OK in the browser closes the slice.

## 6. Close

- Record what was decided along the way: screen specs and `DESIGN.md` for design, the Notion decision log for engineering.
- Work on a branch per slice. Commit finished tasks with conventional-commit messages and no AI attribution. Merge to `main` when the user approves the slice.
- Mark the tasks done in `plan.md` and list follow-ups.
